# Concept: Manacá-Instruct-PT — Instruction-Tuned Version of the Manacá-1B Base Model

- **Slug**: manaca-instruct-pt
- **Created**: 2026-09-14
- **Recommended option**: Option B — Core Lifecycle v1 (curated dataset, full eval, real cross-hardware run, HF publish)
- **Author confirmation (2026-09-14)**: Option B selected.

## Options

### Option A — Minimal Viable Instruct
- **Sketch**: Adapt a single existing PT-BR instruction dataset (per problem.md's open item, most likely `dominguesm/alpaca-data-pt-br` — a ready-made, already-translated Alpaca set) with light filtering toward the five task categories, run one QLoRA pass on the RTX 5050, spot-check against the fixed eval prompts (no rigorous Grupo A/B forgetting study), merge, quantize to GGUF Q4_K_M, confirm it loads and runs on the Dell G3 (no formal benchmark), and publish to Hugging Face with a model card disclosing it as a personal/learning project. This is the "get something real published fast" path.
- **Appetite**: small (matches roadmap-execucao.md's "meta prática mínima" of 3–5 days, plus roughly a day for quantization + HF publish).
- **Trade-offs**: Wins speed and closure — the author reaches a publishable artifact and the core hands-on experience (dataset adaptation → SFT → QLoRA → quantize → deploy → publish) in about a week. Sacrifices rigor: no measured catastrophic-forgetting check (Goal 3 in problem.md), no confirmed tokens/sec on either machine (Success Metric: ~70 tok/s "sem gargalos" is left unverified), and public downloaders get a model whose quality floor is unknown before release — risky given it's meant for strangers on Hugging Face, not just the author.
- **Rabbit holes**: Skipping the fixed-eval baseline (project doc §12–13) to save time is tempting but removes the only way to know if fine-tuning actually helped — this is the one step that should never be cut even in the smallest version.

### Option B — Core Lifecycle v1 (curated dataset, full eval, real cross-hardware run, HF publish)
- **Sketch**: Same starting point as Option A, but treated as a real v1 rather than a shortcut: adapt and curate one or more existing PT-BR instruction datasets (author picks specific source(s) — deferred per problem.md), run the full baseline → dataset prep → QLoRA → **both** Grupo A (new capability) and Grupo B (forgetting-check) evaluation from project doc §30 → at least one iteration round if eval reveals problems → merge → GGUF quantization compared across at least Q4_K_M and one alternative level → a real, measured benchmark run on the Dell G3 (tokens/sec, RAM/VRAM, load time, per project doc §23) → publish to Hugging Face with a model card disclosing the personal/learning framing, documented limitations, and attribution to the CC BY 4.0 base model. No API, UI, or RAG layer — explicitly excluded per problem.md's non-goals.
- **Appetite**: medium (roadmap-execucao.md's own estimate for "v1 completa sem RAG" is ~1.5–2 weeks; trimming the API/UI phases the author's non-goals already exclude brings this closer to ~1–1.5 weeks of active work).
- **Trade-offs**: Wins on both halves of the dual goal in problem.md — genuine lifecycle depth (every stage actually exercised and evaluated, not skipped) and a model the author can stand behind before handing it to strangers on Hugging Face. Sacrifices some speed versus Option A, and the ~70 tok/s target is measured rather than assumed, which risks surfacing that the Dell G3 (4GB VRAM, GTX 1050) can't hit it — a real result, not a guess, but one that may require a scope conversation later if it fails.
- **Rabbit holes**: (1) Dataset curation has no fixed size target — "curate" can expand indefinitely; needs a hard cap agreed before starting. (2) The Grupo A/B forgetting-eval harness (project doc §30–31) doesn't exist yet and must itself be designed, which is real, uncounted work. (3) Hyperparameter iteration (Phase 5) can loop without a stopping rule — cap it at one iteration round unless there's a clear, specific failure to fix. (4) The 70 tok/s target's target hardware is still an open question in problem.md — chasing it on the wrong machine wastes the iteration budget.

### Option C — Full Specialization Suite
- **Sketch**: Everything in Option B, plus the project doc's later-phase ambitions: multiple task-specific LoRA adapters (§9 — Gramática, Jurídico, Atendimento, Acadêmico) instead of one generalist instruct model, deeper multi-round dataset iteration (v2/v3), and a fuller benchmark suite across quantization levels and both machines, published as a small family of Hugging Face artifacts rather than one model.
- **Appetite**: large (weeks to months — this is roadmap-execucao.md's full scope including RAG-adjacent specialization work, without even counting RAG itself).
- **Trade-offs**: Wins on ambition and portfolio depth — a family of specialized adapters is a more impressive, more differentiated public artifact than a single generalist model, and would more directly compete with (rather than sit beside) mature alternatives like Tucano2. Sacrifices the appetite discipline the project's own planning document explicitly recommends against: §37 of manaca-local-projeto.md says outright "a primeira meta deve ser pequena... não começar pela [ambição maior]." Building multiple specializations before the first generalist model is validated inverts the author's own stated sequencing.
- **Rabbit holes**: Nearly everything here is a rabbit hole before Option B's core loop is proven — training N adapters multiplies every unresolved risk in Option B (dataset curation, forgetting eval, hardware benchmarking) by N, with GPU time on a single 8GB card as a hard sequential bottleneck (research.md, roadmap-execucao.md: "mais agentes não encurtam uma rodada de fine-tuning").

### Option D — Don't Build; Adopt an Existing Model
- **Sketch**: Skip fine-tuning Manacá entirely. Either use Tucano2-qwen (already instruction-tuned, 0.5B–3.7B, SFT+APO, published benchmarks beating larger competitors per research.md) directly, or at most publish a lightweight prompt-template/evaluation pack around it, rather than training anything.
- **Appetite**: small (days, mostly documentation and packaging).
- **Trade-offs**: Wins on producing a genuinely strong, publicly-usable PT-BR instruction model immediately, with essentially zero training risk — directly satisfies the "usable, public" half of problem.md's dual goal, likely better than a first DIY attempt could. Sacrifices the entire primary goal: problem.md's Goal 1 is explicitly to *gain hands-on experience executing the lifecycle*, and this option provides none of that — no dataset work, no SFT, no QLoRA, no quantization pipeline of the author's own. It also isn't really "the same idea" anymore; it answers a different problem (get a good PT-BR model) than the one defined (learn by building one from Manacá).
- **Rabbit holes**: None technically — the risk here is entirely strategic: it quietly abandons the reason the project exists, so including it is about completeness of the option set, not because it is likely to be chosen.

## Recommendation

**Option B — Core Lifecycle v1.** It is the only option that scores well against *both* halves of problem.md's confirmed dual goal: it exercises every stage of the lifecycle for real (satisfying the primary learning driver) while producing a model that has actually been evaluated for quality and forgetting and actually benchmarked on the target hardware before being handed to the public on Hugging Face (satisfying the confirmed public-release and "sem gargalos" ~70 tok/s goals). It also matches the appetite the author's own planning documents already converged on independently (roadmap-execucao.md's "v1 completa sem RAG" estimate, and project doc §37's explicit advice to start small and not chase API/UI/RAG first) — this isn't a novel scope imposed from outside, it's closer to a confirmation and tightening of what was already planned, with the untested assumptions (dataset choice, forgetting eval, real hardware numbers) made explicit rather than implicit.

Option A is a reasonable fallback if the author's actual appetite is smaller than it appears — the assessment should flag this to the author as a live choice at decide-time, not silently assume medium appetite. Option C should only be considered after Option B ships and its core assumptions hold. Option D is included for completeness but is a different project, not a smaller version of this one, and is not recommended given the confirmed goal.

## Out of Scope (for the recommended option)

- Any API (FastAPI or otherwise), web/CLI interface, or RAG/document-Q&A layer — explicitly excluded per problem.md's non-goals; these remain optional future local extensions, not part of this concept.
- Multiple task-specialized LoRA adapters (Option C's scope) — deferred until a single generalist Manacá-Instruct-PT is shipped and validated.
- Matching or beating the benchmark quality of mature existing alternatives (Tucano2-qwen and similar) — per problem.md's non-goals, this project's value does not depend on winning that comparison.
- Reproducing the official Manacá pretraining pipeline (Megatron-LM, full corpus retraining) — out of scope per the source project document and problem.md.
- Ongoing support, moderation, or maintenance commitments to public Hugging Face downloaders after release.

## Assumptions to Validate

- That the ~70 tokens/second "sem gargalos" usability target is achievable on at least one of the two machines at a quantization level that still preserves acceptable output quality — problem.md leaves open which machine this target is meant for; `/speckit-specify` should pin this down before implementation, since it changes whether Q4_K_M is sufficient or a higher-bitrate quantization (with a corresponding VRAM/RAM trade-off) is needed.
- That an existing PT-BR instruction dataset (e.g. `dominguesm/alpaca-data-pt-br`, Canarim, or a blend) can be adapted to the five target task categories (grammar correction, rewriting, summarization, simplification, classification) without requiring substantial original authorship — problem.md confirms "existing datasets" as the direction but not which one(s) or how much curation they need.
- That QLoRA fine-tuning behaves well specifically with Manacá's SentencePiece tokenizer and lowercase-normalized text handling (project doc §2.5) — the general 8GB-VRAM QLoRA feasibility evidence in research.md comes from a different model family (Qwen2.5-1.5B on an RTX 4060), not from Manacá itself; the Phase 1 baseline run is the first real test of this for the author's specific case.
- That the Grupo A / Grupo B (new-capability vs. forgetting) evaluation approach described in project doc §30–31 can be designed and executed without disproportionate extra effort — this harness does not exist yet and is new work, not just following an existing recipe.
- That the CC BY 4.0 license on the base model, plus the author's planned "personal/learning project" disclosure, is sufficient for a responsible public Hugging Face release — this is a reasonable default assumption but has not been explicitly confirmed by the author as adequate (e.g., no explicit discussion of a model card's "risks and limitations" section, given the base model's near-chance ARC-Challenge-PT score flagged in research.md).
