# Feature Specification: Data Quality & Evaluation Iteration (Manacá-Instruct-PT v3)

**Feature Branch**: `002-data-quality-iteration`

**Created**: 2026-09-15

**Status**: Draft

**Input**: User description: "Follow-up to `001-manaca-instruct-tuning`, derived from the qlora-v2 audit (`eval/results/qlora-v2-review.md`) and the technical proposal in `specs/002-data-quality-iteration/proposal.md`: make the evaluation trustworthy (blind re-grading, a report that separates fully-correct answers from partial credit, and a measurement of the training-vs-evaluation prompt-structure gap on the existing v2 model), clean the training data (off-task examples mislabeled as grammar/simplification, corrupted targets, duplicates, and classification examples that never use the target labels), make training use a held-out validation set and record full provenance, and run two controlled follow-up training runs to isolate the effect of clean data from the effect of the training objective — since feature 001's single iteration round (FR-005) was consumed by qlora-v2."

## Clarifications

### Session 2026-09-15

- Q: Does this feature's adopted candidate become the published model, or is qlora-v2 published first? → A: Publication waits for this feature. Feature 001's publication step is deferred; the first public release is the candidate adopted here — or qlora-v2, with the blind-regraded numbers, if no candidate passes the adoption rule.
- Q: Where do the new classification seed examples for the four target labels come from? → A: Generated by a language model, then reviewed and edited by the author one by one. - Q: Which existing runs must be re-graded blind for the final comparison table? → A: Only qlora-v2 and the official release (about 176 manual grades; raised to about 264 by the presentation-experiment decision below). Baseline and qlora-v1 keep their existing grades and the table marks them as graded under the earlier, non-blind protocol.
- Q: Where are the grades from a blind re-grading of an existing run stored, given that feature 001's result files are frozen? → A: In a new result file per run (a blind variant of the run identifier) that copies the original answers; the original file is never modified, so both protocols' grades stay available side by side.
- Q: Should the prompt-structure experiment grade qlora-v2 blind under both presentations, so the measured difference is not confounded by the change of grading protocol? → A: Yes. qlora-v2's single-line and separated runs are graded blind, interleaved in one session; the official release is then graded blind under the presentation selected for the final table. About 264 blind grades for existing runs in total.
- Q: How is the "data plus objective" candidate defined so that the response-only objective and held-out checkpoint selection are not bundled into one change? → A: Held-out loss is recorded for every run as instrumentation, but both candidates keep the last-epoch checkpoint as v2 did; the second candidate changes only the objective. If its best-by-held-out checkpoint is not the last epoch, that checkpoint is evaluated as an extra "best checkpoint" row — no retraining, one more blind grading pass.
- Q: If a category ends below the 350-example minimum after cleaning, what sources may be used to bring it back up? → A: First widen that category's selection from the two existing public sources with a verified precision check; if still short, additional public datasets may be added, each with its own license check and model-card disclosure. Filters are never relaxed and generated examples are not used for this purpose; any remaining shortfall is documented.
- Q: In the adoption rule, how should the classification criterion be expressed, given that "three distinct labels" would already be satisfied by qlora-v2's near-miss strings? → A: Replace it with a classification accuracy floor: at least 50% of the 16 classification prompts answered with the correct label (8 of 16). A model that always answers one label scores 25%, so this floor cannot be met by collapsing to a single class.

## User Scenarios & Testing *(mandatory)*

### User Story 1 - Make the existing evaluation trustworthy (Priority: P1)

As the project author, I re-grade the recorded model outputs without knowing which model produced each answer, obtain a per-category report that separates the "fully correct" rate from the partial-credit average, and measure — on the existing qlora-v2 model, without any retraining — how much the mismatch between the training prompt structure (instruction and text separated) and the evaluation prompt structure (everything in one line) affects results.

**Why this priority**: Every later decision (which data problems matter, whether v3 is better than v2, what the model card claims) depends on grades that can be trusted. The audit found grades that look generous, a metric that hides the fact that only 7 of 80 answers were fully correct, and a structural difference between training and evaluation prompts whose effect was never measured. All three can be fixed with no GPU training, so they come first.

**Independent Test**: Can be fully tested by re-grading the qlora-v2 and official-release result files in blind mode, generating the comparison report, and running the v2 model once more with separated prompt structure — this delivers an honest comparison table on its own, even if no new model is ever trained.

**Acceptance Scenarios**:

1. **Given** result files from two or more runs, **When** the author reviews them in blind mode, **Then** neither the model name nor the run identifier is shown for any answer, answers from the different runs are presented in mixed order, and each grade is saved to the correct answer in that run's new blind result file while the original file is left unchanged.
2. **Given** graded result files, **When** the report is generated, **Then** for every task category and every run it shows the partial-credit average, the fully-correct rate, the count of each grade value, and — for any pair of runs — how many individual prompts improved, worsened, or tied.
3. **Given** the existing qlora-v2 model and the frozen evaluation prompts, **When** the prompts are presented with instruction and text separated (the structure used in training) instead of as a single line, **Then** the results are recorded under a distinct run identifier, the frozen prompt text itself is unchanged, both the single-line and the separated runs are graded blind in one interleaved session, and the per-category difference between them is reported.

---

### User Story 2 - Train on clean, on-task data (Priority: P1)

As the project author, I regenerate the training dataset so that it no longer contains examples that are off-task for their category (weather forecasts and code fixes labeled as grammar correction; trivia questions and math labeled as simplification), corrupted target answers, duplicated examples, or classification examples whose answer is not one of the labels offered in the instruction — and I receive a report of what was removed and why, so I can judge whether each category still has enough usable examples.

**Why this priority**: The audit found concrete defects in the data actually used for v1 and v2 (52 "previsão"/"forecast" false positives in grammar, 173 trivia rows in simplification, 26 corrupted classification answers, 58 duplicates, 25 examples shared between training and validation, and zero classification examples using the four labels the evaluation asks for). These are verified facts, not hypotheses about model capacity, so fixing them is the highest-value change to the data.

**Independent Test**: Can be tested by regenerating the dataset from the same public sources and inspecting the preparation report plus a random audit sample — this delivers a verifiably cleaner dataset on its own, independent of whether or when a new model is trained on it.

**Acceptance Scenarios**:

1. **Given** the public source datasets (those used in feature 001, plus any additional public dataset admitted to cover a short category), **When** the dataset is prepared, **Then** no grammar-correction example is a weather-forecast or code-fixing task, no simplification example is a trivia question or a math simplification, every classification example's answer is one of the labels offered in its own instruction, no example has a corrupted (degenerate, repeated-character) answer, and no two examples share the same content within training or between training and validation.
2. **Given** a preparation run, **When** it finishes, **Then** a report lists per-category counts before and after each filter, the number removed per reason, a content fingerprint of the produced files, and a warning for any category that ends below the agreed minimum size.
3. **Given** a set of seed classification examples for the four target labels (complaint, question, praise, request) — generated by a language model and individually reviewed by the author — **When** they are included in preparation, **Then** they pass the same checks as public-source examples, none of them reuses or paraphrases any of the evaluation prompts, no single label exceeds 40% of the set, and the generating model is recorded alongside them.
4. **Given** a random sample of 30 grammar-correction examples kept after filtering, **When** the author audits them, **Then** at least 27 are genuine language corrections.

---

### User Story 3 - Training that measures generalization and records provenance (Priority: P2)

As the project author, I train with a held-out validation set so that I know, for every run, which epoch's checkpoint generalizes best instead of assuming the last one does, I can optionally make training learn only from the response part of each example, and every training and evaluation run leaves a manifest (configuration, data fingerprint, code version, library versions, base-model revision, prompt structure) so that any result can be reproduced and attributed to a single change.

**Why this priority**: v2's training loss fell steadily, but with no held-out measurement it is impossible to say whether that reflected generalization or memorization, and v2 changed data and epochs at the same time, so neither gain can be attributed. This story makes the follow-up runs in Story 4 interpretable; it is less urgent than Stories 1–2 because it changes nothing about what the data or grades say.

**Independent Test**: Can be tested by running a short training job and confirming that held-out loss is recorded each epoch, every epoch's checkpoint is kept, the manifest names the best epoch by that measure, and a complete manifest exists — deliverable on its own, before any full-length run.

**Acceptance Scenarios**:

1. **Given** a training run with training and validation sets, **When** it completes, **Then** held-out loss is recorded for every epoch, every epoch's checkpoint is kept, the run's adapter is the last epoch (as for qlora-v2), and the manifest names the epoch with the lowest held-out loss.
2. **Given** the response-only training objective is enabled, **When** the resulting model answers an evaluation prompt, **Then** it still ends its answer on its own (does not run on until the length limit).
3. **Given** the response-only objective is disabled (the default), **When** training runs, **Then** its behaviour is identical to the process that produced qlora-v2, so v2 remains reproducible.
4. **Given** any training or evaluation run, **When** it finishes, **Then** a manifest records the full configuration, the fingerprint of every dataset file used, the source-code version, the versions of the model-training libraries, the base-model revision, and the prompt structure — and two runs whose manifests are identical used identical inputs.

---

### User Story 4 - Two controlled follow-up runs and a documented decision (Priority: P2)

As the project author, I train two candidate models — one that changes only the data (clean data, training process identical to v2) and one that additionally uses the response-only objective — evaluate both on the frozen prompt set with the same blind grading protocol as Story 1, add the second candidate's best-by-held-out checkpoint as an extra row when it is not the last epoch, compare everything against v2 and the official release, and pick (or decline) a candidate by a rule written down before the runs.

**Why this priority**: This is where the feature produces a better model, if one is achievable; it depends on all three earlier stories and costs GPU time and manual grading, so it comes last among the training-related stories. Isolating "data only" from "data + objective" is what lets the outcome be explained rather than guessed.

**Independent Test**: Can be tested by evaluating both candidates under the Story 1 protocol and applying the decision rule — this delivers a defensible "adopt / do not adopt" answer on its own.

**Acceptance Scenarios**:

1. **Given** the two candidates, **When** both are evaluated on the frozen prompt set under identical prompt structure and blind grading, **Then** a four-way per-category report (v2, data-only candidate, data-plus-objective candidate, official release) is produced with both the partial-credit average and the fully-correct rate — with a fifth "best checkpoint" row whenever the data-plus-objective candidate's lowest-held-out-loss epoch is not its last epoch.
2. **Given** the report, **When** the decision rule is applied, **Then** a candidate is adopted only if it answers at least 8 of the 16 classification prompts with the correct label, reaches a fully-correct rate of at least 20% on the new-capability group, has no category whose average falls below v2's, and shows no more than a 10% relative drop on the forgetting-check group compared to v2 — otherwise the shortfall is documented and v2 remains the final model of feature 001.
3. **Given** the data-plus-objective candidate fails the rule where the data-only candidate passes it, **When** the decision is recorded, **Then** the response-only objective is flagged as the suspected cause and the data-only candidate is the one considered for adoption.
4. **Given** the adopted candidate still falls short of the original 70% per-category target, **When** further single-change runs are considered (model-preparation settings, generation settings, wider adapter coverage), **Then** each run changes exactly one factor, generation-setting comparisons use a separate development prompt set rather than the frozen evaluation set, and at most three such runs are made before the result is documented as-is.

### Edge Cases

- What happens when cleaning leaves a category well below the others (simplification is expected to drop to roughly 350 examples)? The preparation report must warn. The remedies, in order, are: widen that category's selection from the existing public sources with a verified precision check on a sample; then, if still short, add another public dataset after checking its license and disclosing it in the model card. The category's filters are never relaxed, generated examples are not used to fill it, and a remaining shortfall is documented rather than hidden.
- What happens if the blind re-grading lowers v2's scores below the numbers already written in the review documents and model card draft? The blind numbers become the reported numbers; the earlier grades remain in the untouched original result file for provenance and the documents are updated to say why they changed.
- What happens if the prompt-structure experiment shows a large per-category difference (two or more prompts out of sixteen)? Then the separated presentation is selected for the final table (FR-019): the official release and both candidates are evaluated under it, and the table states so. If the difference is smaller, the single-line presentation is kept and the separated results remain documented as the measurement only.
- What happens if the best checkpoint by held-out loss is an early epoch? For the data-plus-objective candidate it is evaluated as its own "best checkpoint" row, so the effect of training length is measured rather than assumed in either direction; in every run the epoch is recorded in the manifest as evidence about training length.
- What happens if a generated classification seed example turns out to resemble an evaluation prompt? Exact reuse is rejected automatically; paraphrases are prohibited by rule, the author checks every generated message against the 16 classification prompts during review and confirms in writing that none were kept. The evaluation prompts remain frozen either way.
- What happens if the terms of the language model used to generate the seed examples restrict how its outputs may be redistributed or used for training? This must be checked before the examples are used, recorded with the examples, and reflected in the model card; if the terms are incompatible with the model's CC BY-NC 4.0 release, the examples are regenerated with a different model or written by the author instead.
- What happens if held-out loss is measured against validation examples that also appear in training? This must be impossible after deduplication and is checked before every run; a run with any overlap is invalid.
- What happens if neither candidate passes the decision rule? qlora-v2 stays the final model of feature 001 and is the one published, with the blind-regraded numbers; this feature ends with the improved evaluation, data, and training tooling as its deliverables, and the shortfall goes into the model card's known limitations.

## Requirements *(mandatory)*

### Functional Requirements

**Trustworthy evaluation**

- **FR-001**: The manual review process MUST offer a blind mode that hides the model name and run identifier from the reviewer, presents answers from multiple runs in a mixed order, and saves every grade to the correct answer in a new result file per run — a blind variant of that run's identifier that copies the original answers — never modifying the original result file.
- **FR-002**: The project MUST produce, from any set of graded result files, a per-category report showing for each run the partial-credit average, the fully-correct rate, the count of each grade value, and — for any pair of runs — the number of prompts that improved, worsened, or tied; the report MUST be in a form that can be pasted into the model card.
- **FR-003**: The project MUST be able to evaluate an existing model with the evaluation prompts presented as separated instruction and text (the structure used in training) without altering the frozen prompt text; the separated fields MUST reconstruct the original prompt text exactly, and results MUST be recorded under a run identifier distinct from the single-line evaluation.
- **FR-004**: qlora-v2 MUST be graded under the blind protocol under both presentations (single-line and separated, interleaved in one session), the official release MUST be graded blind under the presentation selected for the final table (FR-019), and every new candidate MUST be graded under the blind protocol. The baseline and qlora-v1 runs keep their existing grades, and every table that includes them MUST mark them as graded under the earlier, non-blind protocol.
- **FR-005**: A development prompt set of about 10 prompts per task category, with reference answers, drawn from the cleaned validation data, MUST be used for any comparison of generation settings or other tuning decisions; the frozen evaluation set MUST be used at most once per final candidate.

**Clean training data**

- **FR-006**: Grammar-correction selection MUST match whole words only (so "previsão" no longer matches "revisão") and MUST exclude instructions about fixing code.
- **FR-007**: Simplification selection MUST exclude trivia-question tasks and mathematical simplification, and MUST require a text to be simplified to be present.
- **FR-008**: Classification selection MUST keep only examples whose answer is short (at most four words) and is one of the labels offered in that example's own instruction.
- **FR-009**: Dataset preparation MUST reject, for every category, answers that are degenerate (long runs of a repeated character or repeated short sequence, or extremely low character variety).
- **FR-010**: Dataset preparation MUST remove duplicates by normalized content (first by instruction + text + answer, then by instruction + text) before shuffling, capping, or splitting, so that no content is shared between the training and validation files.
- **FR-011**: The project MUST add seed classification examples for the four target labels (complaint, question, praise, request), at least 30 per label, in the same instruction wording as the evaluation prompts, with no label exceeding 40% of the set, marked with a distinct source, and subject to the same validation and no-overlap checks as public-source examples. These examples are generated by a language model and MUST each be reviewed (kept, edited, or discarded) by the author before use; the generating model and its usage terms MUST be recorded with the examples, the terms MUST be compatible with the model's CC BY-NC 4.0 release, and the author MUST confirm that no kept example reuses or paraphrases an evaluation prompt.
- **FR-012**: Dataset preparation MUST write a report with per-category counts before and after each filter, the number removed per reason, the number of examples contributed by each source, a content fingerprint of the produced training and validation files, and a warning for any category ending below 350 examples. A category below that minimum MUST be remedied only by, in order: widening its selection from the existing public sources with a verified precision check on a sample, then adding further public datasets (FR-013) — never by relaxing the category's filters or by generated examples; any remaining shortfall is documented.
- **FR-013**: The total prepared dataset MUST remain within the 3,000–5,000 range agreed in feature 001, and its license determination (CC BY-NC 4.0, inherited from the public sources) MUST remain unchanged. Any additional public dataset MUST, before use, be checked for terms compatible with that release, and MUST be listed — with its license and the number of examples it contributed — in the preparation report and in the model card.

**Training with validation and provenance**

- **FR-014**: Training MUST evaluate a held-out validation set at least once per epoch, record the result, keep every epoch's checkpoint, and name the epoch with the best held-out result in the run manifest; the run's adapter remains the last epoch (as for qlora-v2), so held-out evaluation is instrumentation and never silently changes which model a run produces.
- **FR-015**: Training MUST offer a response-only objective (learning only from the answer portion of each example) that is off by default so that qlora-v2 remains reproducible; when on, the resulting model MUST still terminate its answers on its own.
- **FR-016**: Every training run and every evaluation run MUST write a manifest containing the full configuration, fingerprints of all dataset files used, the source-code version, the versions of the training/inference libraries, the base-model revision, and the prompt structure used.
- **FR-017**: Every training run MUST start from the base model (no run continues from a previous adapter), so that each run is attributable to its own data and configuration.

**Controlled follow-up runs**

- **FR-018**: The project MUST train exactly two primary candidates, both keeping the last-epoch adapter: one that uses the cleaned data with a training process otherwise identical to qlora-v2, and one that additionally enables the response-only objective; the two MUST differ in nothing else. If the data-plus-objective candidate's best-by-held-out epoch is not its last epoch, that checkpoint MUST be evaluated as an additional "best checkpoint" row of the final table without any retraining; the same applies to the data-only candidate only when it is the one under consideration for adoption.
- **FR-019**: The presentation used for the final table MUST be selected by the presentation experiment (FR-003): separated if qlora-v2's blind grades differ by two or more prompts (out of sixteen) in any category between the two presentations, otherwise single-line. Every row of the final table — both candidates, qlora-v2, and the official release — MUST be evaluated under that one presentation and graded under the blind protocol, and the table MUST state which presentation was used.
- **FR-020**: A candidate MUST be adopted only if it meets all of: at least 8 of the 16 classification prompts answered with the correct label (a 50% accuracy floor, above the 25% that answering a single label for everything yields); a fully-correct rate of at least 20% on the new-capability group; no category average below qlora-v2's blind grades under the selected presentation; and no more than a 10% relative drop on the forgetting-check group compared to those same qlora-v2 grades. If no candidate qualifies, qlora-v2 remains feature 001's final model and the shortfall is documented.
- **FR-021**: Any further run beyond the two candidates MUST change exactly one factor, MUST be justified by the candidates' results, and MUST be limited to three such runs in total.
- **FR-022**: The evaluation prompt texts, the recorded result files of feature 001 (baseline, qlora-v1, qlora-v2, official release), the qlora-v1 and qlora-v2 adapters, and the qlora-v2 quantized artifacts MUST NOT be modified; every new result is written to a new file under a new run identifier.

**Reporting**

- **FR-023**: Feature 001's publication step MUST wait for this feature's decision (FR-020): the first public release is the adopted candidate, or qlora-v2 if no candidate qualifies. The published model card MUST report both the partial-credit average and the fully-correct rate per category, mark which runs were graded under the blind protocol and which under the earlier one, state that classification in qlora-v2 collapsed to a single label, list every public dataset used with its license and contribution, and disclose that the seed classification examples were generated by a named language model, reviewed by the author, and target the customer-service domain of the evaluation.

### Key Entities *(include if feature involves data)*

- **Blind Review Session**: A manual grading pass over one or more result files in which model and run identity are hidden and presentation order is mixed; produces, for each run reviewed, a new blind result file (a copy of that run's answers carrying the blind grades) and leaves the original result file untouched.
- **Grading Report**: The per-category, per-run summary (partial-credit average, fully-correct rate, grade distribution, pairwise improved/worsened/tied counts) generated from graded result files; the source of every number in the model card.
- **Separated Evaluation Prompt**: A frozen evaluation prompt annotated with its instruction and text as separate parts, reconstructing the original text exactly; used to present prompts in the training structure without changing what is asked.
- **Preparation Report**: The record of a dataset-preparation run — counts per category before and after each filter, removals per reason, examples contributed per source (with each source's license), content fingerprints, and any under-minimum warnings.
- **Seed Classification Examples**: Classification examples for the four target labels generated by a language model and individually reviewed by the author, kept in their own source with a record of the generating model and its terms, subject to the same validation and no-overlap rules as public-source examples.
- **Development Prompt Set**: About 10 prompts per category with reference answers, drawn from cleaned validation data, used for tuning decisions so that the frozen evaluation set is not reused.
- **Run Manifest**: The provenance record of a training or evaluation run (configuration, dataset fingerprints, code version, library versions, base-model revision, prompt structure).
- **Candidate Model**: One of the two primary follow-up runs — "data only" and "data plus objective" — each starting from the base model, keeping its last-epoch adapter, and differing from the other in exactly one factor. A candidate's "best checkpoint" row is the same run's lowest-held-out-loss epoch evaluated separately, without retraining.

## Success Criteria *(mandatory)*

### Measurable Outcomes

- **SC-001**: qlora-v2 and the official release have been re-graded under the blind protocol, and a report exists showing both the partial-credit average and the fully-correct rate for every task category.
- **SC-002**: The measured effect of prompt structure on qlora-v2 is documented as a per-category difference between the single-line and separated presentations, both graded under the blind protocol, together with the presentation selected for the final table and the rule that selected it.
- **SC-003**: The regenerated training data contains zero examples matching any of the audited defect patterns (forecast/code tasks in grammar, trivia/math in simplification, corrupted answers, content duplicates, training/validation overlap), 100% of classification answers appear among the labels offered in their instruction, and a 30-example grammar audit finds at least 27 genuine corrections.
- **SC-004**: The regenerated dataset totals between 3,000 and 5,000 examples, and every category either has at least 350 examples or its shortfall is documented with the reason.
- **SC-005**: Every training and evaluation run performed in this feature can be traced through its manifest to a specific data fingerprint, configuration, and code version; preparing the dataset twice from the same sources yields the same fingerprint.
- **SC-006**: The adopted candidate (if any) answers at least 8 of the 16 classification prompts with the correct label (qlora-v2: 4, all the same label), and reaches a fully-correct rate of at least 20% on the new-capability group (qlora-v2: 8.75%).
- **SC-007**: The adopted candidate (if any) has no category average below qlora-v2's and no more than a 10% relative drop on the forgetting-check group compared to qlora-v2.
- **SC-008**: Whether or not a candidate is adopted, the decision and the four-way comparison are written down with the rule that produced them, and the model card of the first public release reports both metrics per category and marks which runs were graded blind.

## Assumptions

- The author is the only grader; blind presentation is the mitigation for single-grader bias, and reporting the fully-correct rate alongside the partial-credit average further reduces sensitivity to generous partial grades.
- The 70% per-category target from feature 001 is not this feature's bar; this feature's bar is a verifiable, attributable improvement over qlora-v2 under an honest protocol (FR-020), with the 70% target remaining a documented aspiration.
- The two candidates each take roughly 10–15 minutes of training on the author's development machine, so the GPU cost of the feature is small; the dominant cost is manual grading — about 88 answers per run under the blind protocol, about 264 for the existing runs (qlora-v2 under both presentations, the official release under the selected one) plus 88 per candidate.
- Seed classification examples deliberately target the customer-service domain of the evaluation prompts (complaint / question / praise / request); this bias is intentional and is disclosed rather than avoided.
- Adding seed examples does not change the model's license: the public sources that impose CC BY-NC 4.0 remain part of the blend. The usage terms of the language model that generates the seed examples are assumed to permit this use, but must be checked and recorded before the examples are adopted (FR-011).
- The base model and the two public source datasets from feature 001 are unchanged; the only reasons for dataset differences are the new filters, deduplication, the seed examples, and any additional public dataset admitted under FR-012/FR-013 to cover a short category.
- Feature 001's second-machine benchmark and model-card drafting proceed on their own schedule; only its publication step waits for this feature's decision (FR-023). The already-quantized qlora-v2 artifacts stay as they are and are what gets published if no candidate qualifies.
- Decisions in Story 4 use the grades produced under this feature's blind protocol, not the grades recorded before it; the baseline and qlora-v1 numbers are context only and are never part of the adoption rule.
